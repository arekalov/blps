# План доработки проекта под лабораторную работу №3

**Гранулярный пошаговый план (фазы A–L, чеклист):** см. корневой [`plan.md`](../plan.md) в репозитории.

Документ фиксирует **согласованную с собой** траекторию доработки текущего приложения (лабораторная №2) под требования лабораторной №3 из [`README.md`](../README.md). Перед сдачей прецеденты и контракты API нужно **подтвердить с преподавателем** — для консультации используйте чеклист [LAB3_STAGE2_TEACHER_CHECKLIST.md](LAB3_STAGE2_TEACHER_CHECKLIST.md).

**Актуальные решения:** (1) начинать с **отказа от WildFly** (JAR + embedded Tomcat); (2) **без** Gradle-модуля `common` — в worker **дублируются** минимальные JPA-классы; (3) **одна БД** — как в профиле **`dev`** ([`application-dev.yaml`](../src/main/resources/application-dev.yaml)), локальный Postgres в Docker **не обязателен**; (4) в compose на первом этапе достаточно **ZooKeeper + Kafka**. **Согласовано с преподавателем** (этап 2): отправка события модерации — **явный** `KafkaProducer` + `ProducerRecord`; **упрощённый** вариант (сразу `PENDING_MODERATION` в main) **не** используем — см. [LAB3_STAGE2_TEACHER_CHECKLIST.md](LAB3_STAGE2_TEACHER_CHECKLIST.md).

## 1. Исходная точка (что уже есть)

- **Домен:** публикация вакансий (hh-подобный сценарий), тарифы, модерация, роли (Spring Security + JAAS), JTA/WildFly по лабе 2.
- **WildFly:** для лабораторной №3 по [`README.md`](../README.md) **не обязателен**. `worker-service` — всегда отдельный Spring Boot **JAR** без сервера приложений. **main-service** можно перевести на **исполняемый JAR + встроенный Tomcat** (убрать `war`, JNDI, `JBossAppServerJtaPlatform`), если согласовано с преподавателем относительно требований лабы №2. JCA к EIS часто снова тянет сервер с RA — учесть при выборе интеграции.
- **Ключевые операции в текущей реализации (main + worker):**
  - отправка на модерацию: `publishVacancy` → **`SUBMISSION_PENDING`**, после commit — событие в Kafka; **worker** идемпотентно переводит в **`PENDING_MODERATION`**; HTTP **`202 Accepted`**;
  - модерация — `ModerationService.approveVacancy` / `rejectVacancy`;
  - архивирование — вручную (`archiveVacancy`) + **`@Scheduled`** автоархив `PUBLISHED` по сроку тарифа.
- **Артефакты для обновления по правилам лабы:** BPMN/модель процесса, OpenAPI, скрипты тестов, при полном объёме лабы — ещё **JCA/EIS** и deployment diagram (см. раздел 7).

## 2. Выбранные прецеденты (фиксация решения)

### 2.1. Асинхронная обработка через Kafka — **вариант 1**

**Прецедент:** работодатель **отправляет вакансию на модерацию** (сейчас это по сути `PATCH …/publish` / `publishVacancy`).

**Идея:** часть работы переносится на **второй узел**: после HTTP-запроса основной сервис **не** выполняет полностью финальный переход в состояние очереди модерации сам в одном синхронном шаге, а **публикует событие** в Kafka; **обработчик на другом узле** доводит доменное состояние до «вакансия в очереди на модерацию» и может выполнить дополнительную логику (приоритет, предварительная проверка, логирование, резерв под интеграции).

**Обоснование для отчёта:** публикация на модерацию в реальных системах часто сопровождается тяжёлыми или вынесенными шагами (антифрод, стоп-слова, обогащение); асинхронная модель с **подпиской** на топик это отражает.

**Топик (рабочее имя, уточнить в коде):** например `vacancy.submitted-for-moderation` (один топик — модель **подписки**: несколько консьюмеров в одной **consumer group** на двух узлах делят партиции).

**Требования методички:**

| Требование | Как закрываем |
|------------|----------------|
| Apache Kafka + ZooKeeper | `docker-compose`: ZK + Kafka (например Confluent-образы или bitnami). |
| Модель «подписка» | Consumer **подписан** на топик (`subscribe` / `@KafkaListener` с `group.id`). |
| Producer API | **Согласовано:** отправка через **`KafkaProducer` + `ProducerRecord`** (явный API). `KafkaTemplate` не как основной способ для этого события. |
| Клиент Kafka на Spring Boot | Консьюмер во **втором** Spring Boot приложении (`@KafkaListener` или явный `KafkaConsumer` в managed-потоке). |
| Два независимых узла | Два отдельных процесса: **main-service** (REST + продюсер + планировщик) и **worker-service** (консьюмеры Kafka, без публичного REST). Альтернатива — два инстанса **одного** артефакта с одной `group.id`; в этом плане зафиксирована схема **main + worker** как в обсуждённом плане. |

### 2.2. Планировщик — **вариант 1**

**Прецедент:** **автоматическое архивирование** опубликованных вакансий по истечении срока размещения, заданного тарифом (`durationDays` относительно момента публикации / начала действия тарифа — **точную формулу** зафиксировать в модели и в коде).

**Сейчас:** срок тарифа учитывается при одобрении (`TariffUsageHistory`), но **авто-ARCHIVED** по календарю может отсутствовать — его добавляем.

**Реализация по методичке:** Spring **`@Scheduled`** + `@EnableScheduling` на узле, где крутится бизнес-доступ к БД (логично — **main-service**).

**Расписание (черновик):** например ежедневно в 03:00 (`cron = "0 0 3 * * *"` по серверному времени контейнера).

**Важно при двух узлах:** если когда-нибудь поднимете **два инстанса main-service**, джоб архивирования может выполниться **дважды** — нужны идемпотентность (`UPDATE … WHERE status = PUBLISHED AND …`) или распределённая блокировка. При **одном** инстансе main-service проблемы нет.

## 3. Термины: брокер, продюсер, консьюмер, узлы

| Компонент | Что это | Где живёт в плане |
|-----------|---------|-------------------|
| **Брокер Kafka** | Сервер очередей/лога сообщений, топики, партиции | отдельный контейнер (процесс), **не** код приложения |
| **ZooKeeper** | координация для классической схемы Kafka | отдельный контейнер |
| **Producer** | код, который **пишет** сообщение в топик | **main-service** (после валидации прецедента «отправка на модерацию») |
| **Consumer** | код, который **читает** топик и обрабатывает сообщения | **worker-service** |
| **Узел 1** | JVM-процесс **main-service**: весь **синхронный REST**, как сейчас, + продюсер Kafka + `@Scheduled` |
| **Узел 2** | JVM-процесс **worker-service**: только обработка сообщений из Kafka (+ доступ к той же PostgreSQL) |

**Синхронный REST** обслуживается **только main-service**: списки вакансий, создание/редактирование, тарифы, модерация и т.д. остаются **синхронными**, кроме эндпоинта (или сценария), который вы переводите на модель «запрос принят → обработка асинхронно» (см. раздел 4).

**worker-service** внешним клиентам **не обязан** открывать HTTP API; достаточно Kafka + БД.

## 4. Поведение REST для прецедента «отправка на модерацию»

Нужно **явно** описать в OpenAPI и показать в отчёте один из контрактов (согласовать с преподавателем).

**Рекомендуемая связка (минимум гонок):**

1. **main-service** при `PATCH …/publish` (или выбранном пути):
   - проверяет права, роль, наличие тарифа, статус `DRAFT` (как сейчас);
   - в **одной транзакции** с БД переводит вакансию в **промежуточный** статус (например `SUBMISSION_PENDING` / `QUEUED_FOR_MODERATION`) **или** оставляет договорённое состояние, при котором редактирование запрещено;
   - после **commit** публикует событие в Kafka (лучше **после коммита**: `@TransactionalEventListener(Phase.AFTER_COMMIT)` или transactional outbox);
   - отвечает клиенту **`202 Accepted`** + тело с `vacancyId` и текущим статусом / ссылкой на `GET /vacancies/{id}`.

2. **worker-service** по сообщению:
   - идемпотентно переводит вакансию в `PENDING_MODERATION` (если ещё не в нём);
   - опционально: поля «назначенный модератор», приоритет — если заложите в модель.

**Альтернатива (проще по UX, слабее по «асинхронности»):** ~~статус сразу `PENDING_MODERATION` в main~~ — **не используем** (согласование этапа 2).

## 5. Сообщение в Kafka (контракт)

Минимальный payload (JSON):

- `eventId` (UUID) — для идемпотентности и логов;
- `vacancyId`;
- `employerId` (опционально);
- `occurredAt` (ISO-8601);
- версия схемы `schemaVersion`.

**Ключ сообщения:** `vacancyId` — чтобы упорядочить события по одной вакансии в одной партиции (если топик многопартиционный).

## 6. Планировщик: автоархивирование

1. Добавить сервис/компонент, например `VacancyArchivingScheduler`:
   - `@Scheduled(cron = "0 0 3 * * *")` (или иной cron по согласованию);
   - запрос к БД: вакансии в статусе `PUBLISHED`, у которых истёк срок по правилу «`publishedAt` + `durationDays` тарифа» (или по `TariffUsageHistory`, если так точнее по домену);
   - массовое обновление в `ARCHIVED` + `updatedAt`.

2. Обновить **BPMN** и описание процесса: появился автоматический переход `PUBLISHED → ARCHIVED`.

3. Не ломать ручное архивирование существующим API.

## 11. Краткая схема потоков

```text
Клиент ──HTTP──► main-service ──► PostgreSQL
                    │
                    │ ProducerRecord
                    ▼
                 Kafka (topic: vacancy.submitted-for-moderation)
                    │
                    │ poll / @KafkaListener
                    ▼
              worker-service ──► PostgreSQL
                    │
                    └── (статус PENDING_MODERATION, …)

main-service ── @Scheduled ──► PostgreSQL (ARCHIVED по истечении срока)
```
